# Аудит MIRAGE перед переходом на Futures

## Проверенные участки исходного проекта

Проверены центральные участки, влияющие на торговый цикл и его отображение: `app/worker.py`, `app/signals.py`, `app/market_data.py`, `app/paper_trading.py`, `app/risk_engine.py`, `app/database.py`, `app/migrations.py`, `app/config.py`, `app/main.py`, `app/platform_api.py`, `app/mirage4_api.py`, `app/intelligence_api.py`, `app/historical_research.py`, `app/signal_intelligence_api.py`, `frontend/app.js`, а также тесты релизного ядра, тесты исторического загрузчика и frontend-контрактов. Проверены usages всех `settings.*` полей в доступных основных модулях на предмет совместимости конфигурации.

## Выявленное исходное состояние

- Сканер получал свечи через общую Spot-oriented реализацию `market_data.get_klines`.
- Paper Trading открывал Long/Short-подобную запись, но P&L был рассчитан как спотовая покупка/продажа без фьючерсной маржи, плеча, funding и ликвидации.
- Открытые позиции проверялись по одиночной текущей Spot-цене в цикле сканера с большим интервалом. Касание SL внутри цикла могло быть пропущено.
- В БД не было однозначного поля рынка, поэтому нельзя было безопасно отличать старые Spot позиции от новых Futures.
- Ручное закрытие позиции и исторический загрузчик тоже использовали Spot endpoints.
- UI не показывал тип контракта, плечо, маржу, funding и ликвидационную оценку.

## Внесённая модель

- Новые сигналы маркируются `usdt_perpetual_futures`; старые записи мигрируются как `spot`.
- Новые стратегии и новые позиции используют публичный Binance USDⓈ-M Futures API. Futures запросы не переключаются на Spot при ошибке.
- Старые открытые Spot позиции продолжают использовать отдельный Spot quote path и старую спотовую формулу закрытия.
- Futures позиции имеют поля `market_type`, `leverage`, `margin_used`, `liquidation_price`, `entry_fee`, `funding_pnl`, `last_funding_time`, `last_mark_check_at`.
- Расчёт размера позиции включает стоп-расстояние, round-trip taker fees и slippage. Лимит убытка не умножается на плечо.
- Funding cashflow списывается/зачисляется по направлению и реальному funding event timestamp с защитой от повторного учёта.
- Mark Price используется как trigger reference для стопов и мониторинга ликвидации.
- Если Stop Loss и Take Profit затронуты в одной минутной свече, используется неблагоприятное разрешение: Stop Loss первым.

## Сохранение данных

Миграция только добавляет nullable/defaulted колонки; прежним строкам присваиваются `spot` и `1x`. Не меняет `balance`, `initial_balance`, P&L, направление, цены, количество, даты и статусы исторических сделок. Начальный виртуальный капитал остаётся текущим, ожидаемо $10,000 суммарно по четырём strategy accounts.

## Валидация

Тесты архива покрывают:
- выбор плеча и верхнее ограничение 8x;
- расчёт ликвидационной оценки и запрет опасного плеча;
- неизменность риск-бюджета при изменении плеча;
- P&L линейного USDT perpetual без искусственного умножения на leverage;
- знаки funding для Long/Short;
- касание SL/TP, одновременное касание, gap-through-stop, проскальзывание;
- отсутствие Futures → Spot fallback;
- добавление схемы без потери баланса и старой Spot-классификации;
- открытие Futures Paper позиции и списание entry fee;
- закрытие по минутной Mark Price свече;
- продолжение защитного SL-контроля при временной ошибке funding API;
- неизменность legacy Spot accounting.

## Оставшиеся внешние проверки

1. Нужно проверить реальный сетевой доступ Render Oregon к `fapi.binance.com`. Эта среда не предоставила способ выполнить исходящий тест из самого Render.
2. Нужен полный прогон тестов исходного репозитория после применения patch, включая обновлённые Spot→Futures mock-ожидания для исторического загрузчика. В текущем исполнении исходный репозиторий не удалось клонировать из runtime; поэтому локальные тесты — тесты новой поставки, а не полный исходный CI.
3. Liquidation price приблизительная: используется фиксированный MMR, а не индивидуальная Binance maintenance-margin bracket таблица. В UI и API поле явно называется оценкой.
4. Проверка Mark Price выполняется каждые 5 секунд и по минутному OHLC, не через тиковой WebSocket поток. Миллисекундную реакцию гарантировать нельзя.

## Примечание к GitHub Upload Pack

Для применения без локального терминала в комплект добавлен `.github/workflows/apply-mirage-futures-patch.yml`. При загрузке файлов в отдельную ветку `mirage-futures-upload` workflow сверяет родительский commit с зафиксированной базой, проверяет и применяет `INTEGRATION_PATCH.diff`, запускает `compileall` и записывает интеграционные изменения отдельным commit в ту же ветку. Если базовый commit не совпадает или patch не применяется чисто, workflow прекращает выполнение без интеграционных изменений. Это не запускает тестовый suite приложения и не выполняет deployment.
